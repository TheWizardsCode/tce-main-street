# Card packs — authoring, building, installing and gating (Main Street)

This runbook walks the full card-pack lifecycle end to end — **authoring →
building → installing → gating** — from the Main Street perspective. It is the
operational companion to
[`docs/DEVELOPER.md → Card Packs`](../../core/docs/DEVELOPER.md#card-packs)
(the engine-side reference, which this file mirrors from the game side) and
[`packs/README.md`](../../packs/README.md). The engine runbook lives at
`core/docs/dev/card-packs-runbook.md`; this file records the Main Street
specifics that differ — the bundled pack source, the pack-art registry, the
production residential pack, and the regenerated self-contained assets.

A **card pack** extends the *already-installed* game with new cards (and
optional art) through the launcher's content directory, **without rebuilding
the launcher**. It is the card-level sibling of the
[runtime game plugin](../../core/docs/dev/runtime-game-plugins-runbook.md)
channel; a pack is a manifest + a CSV fragment in the **game's existing card
schema** + optional assets, and may be entitlement-gated (Steam DLC). Packs are
additive — a pack adds rows, it never replaces or rebalances the base pool.

## Contract at a glance

```
<contentDir>/packs/
  manifest.json                 # pack catalogue ({ version, packs[] })
  <gameId>/<packId>/
    cards.csv                   # CSV fragment (header matches the base pool)
    assets/…                    # pack art, served over tce-packs://
```

Each `manifest.json` entry declares:

| Field | Required | Meaning |
|-------|----------|---------|
| `id` | yes | Stable pack id; also the pack directory name. |
| `gameId` | yes | The game the pack extends (`main-street`). |
| `title` | yes | Display name in the in-game listing. |
| `description` | yes | Short description in the listing. |
| `version` | yes | Pack content version (independent of game/engine). |
| `coreEngineVersion` | yes | Semver **range** the pack supports (e.g. `^0.1.0`). |
| `cards` | yes | Pack-relative path to the CSV fragment. |
| `assets` | no | Pack-relative asset paths (served via `tce-packs://`). |
| `entitlement.steamAppId` | no | Steam DLC app id that unlocks the pack; absent = free. |

The contract is parsed and validated by the core engine
(`core/src/core-engine/CardPackManifest.ts`, `parseCardPackManifest` +
`splitPacksByCompatibility`) and **never throws**: a malformed document,
duplicate ids, and core-incompatible packs are reported structurally and never
applied.

## Prerequisites

- Dependencies installed (`npm install`).
- `tsx` available (a devDependency) — the builder runs under it.
- The **base game's** `card-data.csv` header to copy into the fragment
  (`src/card-data.csv`; 54 columns).
- For the gated scenario, a Steam DLC app id and a launcher build that ships
  the catalog entry (see [Gating a pack](#4-gate-a-pack-optional)).

## 1. Author a pack

A pack source is a directory laid out **exactly like the on-disk target** — a
`manifest.json` (`{ version, packs[] }`) plus one `<gameId>/<packId>/`
directory per pack, owned by the game repo under `packs/`:

```
packs/
  manifest.json
  main-street/<packId>/
    cards.csv
    assets/
      <cardId>.png
```

The committed `packs/` tree is a single source of truth: the card-pack builder
turns it into an installable packs root under `<contentDir>/packs/` **and** the
web build bundles it directly through
`src/MainStreetPackSources.ts` (`import.meta.glob`), so the published browser
build discovers the pack with **no manual copy step** for the bundled source.

### Worked example — the production residential pack

The production pack is `main-street-residential-pack`
(`packs/main-street/main-street-residential-pack/`): ten residential-themed
cards (business, event, upgrade, staff, community-space) generated by
`src/scripts/generate-residential-pack-art.mjs`, gated on the launcher's
unified content-unlock store (unlock key
`dlc:main-street:main-street-residential-pack`).

Authoring rules:

- **Reuse the base header exactly** (same columns, same order) — the merge
  rejects a fragment whose header differs.
- **Use fresh, pack-scoped ids** (e.g. `biz-ms-residential-solar`) — a card id
  that already exists in the base pool or another pack is a **duplicate
  conflict**, and the offending pack is dropped **whole**.
- **Only add rows.** A pack cannot remove or replace a base card.
- Art assets must be listed in the manifest's `assets` and exist under the pack
  directory. Name each asset `<cardId>.png` so the loader can key it by card id
  (Option A: the asset filename stem is the card id).
- All art must be project-generated (CC0) and licence-clean; credit it in the
  game's credits file.
- **Pack art is self-contained.** A pack's declared `assets/<cardId>.png` are
  the **only** art it needs — the base `src/card-art-map.json` is base-pool
  only and is **not** a pack dependency. A third-party pack that has no art
  generated into the game repo still renders its bespoke faces from its own
  assets.

### Pack art (self-contained)

The pack's assets are inlined end to end:

1. The core loader (`core/src/ui/CardPackLoader.ts`) reads each declared asset
   through the injectable `fetchAsset(url) => Promise<Uint8Array>` transport
   (default `fetch` + `arrayBuffer`) and inlines the bytes as
   `data:<media>;base64,…` URIs keyed by card id (the asset filename stem) on
   `LoadedCardPack.assetDataUris` (cross-repo core seam `CG-0MV590RLL0026M7G`).
   The runtime resolver contains **no scheme-specific branching** between
   `tce-packs://` and bundled browser URLs, so the same path works unchanged
   once the browser distribution supplies asset URLs (`MS-0MV1O7EGG004MWGD`).
2. `bootstrapMainStreetCardPacks()` registers every loaded pack's inlined
   assets into the pack-art registry (`src/MainStreetCardPackArt.ts`)
   **before** `MainStreetSvgTextureManager` generates textures, so render-time
   resolution is synchronous.
3. `MainStreetCardArt.getCardArtDataUriForCard(cardId, cardName)` resolves a
   card from the pack registry (by card id) → the base name-keyed map →
   `Fallback`. Base-card resolution is unchanged.

**Graceful degradation.** A pack that fails to load leaves the registry
base-only and the game still boots. A missing/unreadable/malformed asset is
reported structurally and omitted — the card degrades to the base map and then
`Fallback` art with a logged warning, never a crash or a blank face.

## 2. Build a pack

The reference builder validates the source, copies its real (non-symlink) files,
and upserts the manifest entry into an installable **packs root**:

```bash
npm run build:card-pack -- --input packs
```

`build:card-pack` runs the deterministic asset emission **first**
(`npm run generate:pack-assets`, `node src/scripts/generate-residential-pack-art.mjs`),
which emits each pack's `assets/<cardId>.png` as 256×256 PNGs from the
committed `src/sprites/<Name>_1024_x_1024.png` sources (byte-identical for
identical inputs), then invokes `core/scripts/build-card-pack.mjs` with
`--input packs`.

Output:

```
build/card-packs/packs/
  manifest.json                         # merged (upserted, not overwritten)
  main-street/main-street-residential-pack/
    cards.csv
    assets/…                            # the ten <cardId>.png assets
```

Options (of the underlying `build-card-pack.mjs`):

| Flag | Default | Meaning |
|------|---------|---------|
| `--input <dir>` | *required* | Pack source root (manifest + pack dirs). |
| `--out <dir>` | `build/card-packs/packs` | Packs root to write. |

Builder behaviour that matters operationally:

- An **invalid manifest refuses the build** (exit non-zero, nothing written).
- A malformed individual pack (missing directory, missing/invalid CSV, header
  without `id`, or a fragment path that escapes the pack directory) is
  **rejected whole** and printed to the summary; the build then exits non-zero.
- The manifest is **upserted** by `(gameId, id)` and sorted deterministically,
  so building several packs (or rebuilding one) preserves the others and
  produces byte-identical output for equal inputs.
- Symlinks are skipped — they point at shared core assets the launcher already
  ships.

## 3. Install a pack

A pack is installed by copying the built packs root into the launcher's
**content directory**, under `packs/`:

```bash
cp -r build/card-packs/packs <contentDir>/packs
```

The launcher resolves `<contentDir>` (first match wins): `--content-dir <dir>` /
`TCE_CONTENT_DIR` (the Steam DLC-install model), then the bundled `dist/`
(default). For a dev build, install into `dist/packs/` *after* building and
launch Electron directly — do **not** re-run `npm run start:electron`
afterwards, because it rebuilds `dist/` and clears the packs.

At boot the renderer **discovers** the packs for the running game with
`loadCardPacks` (`core/src/ui/CardPackLoader.ts`): it reads
`<contentDir>/packs/manifest.json` through `fetch`, filters by `gameId` and
`coreEngineVersion`, resolves entitlement, and reads each entitled pack's CSV
fragment through the scoped `tce-packs://` scheme. Main Street bootstraps this
**before scene setup** via `bootstrapMainStreetCardPacks()`, so the first deal
already includes pack cards. The inlined pack assets are registered into
`src/MainStreetCardPackArt.ts` at the same point (see
[Pack art (self-contained)](#pack-art-self-contained)).

## 4. Gate a pack (optional)

A pack is **free** when its manifest entry declares no `entitlement`. Main
Street gates the production residential pack on the launcher's unified
content-unlock store (`src/MainStreetContentUnlockGate.ts`)
— lock key `dlc:main-street:main-street-residential-pack`, purchase rule
`main-street-residential-pack-purchase` — so a scoped simulated purchase in the
in-game Card Packs panel unlocks it without collateral-unlocking other rewards.
While locked, its cards stay out of play.

Steam DLC gating (engine-level) is handled by the core entitlement seam
(`core/electron/card-pack-entitlements.ts` + the Steamworks adapter); see the
[engine runbook](../../core/docs/dev/card-packs-runbook.md#4-gate-a-pack-optional)
for the operator catalog (`electron/card-pack-dlc-catalog.json`) and the
`free` / `unlocked` / `locked` listing states.

## 5. Degradation behaviour

Every layer is **total** — a failure degrades to base content, never a crash:

| Failure | Behaviour |
|---------|-----------|
| No content directory (browser / core-only) | Base content; no packs discovered. |
| Missing/malformed `packs/manifest.json` | Reported structurally; base content. |
| Pack `coreEngineVersion` incompatible | Hidden from play; listed as incompatible with a reason. |
| Gated pack not owned / Steam unavailable | Listed locked with a reason; its cards are absent. |
| Pack CSV header mismatched, or duplicate card id | Pack dropped **whole** (never partially merged). |
| Failed CSV/asset read | Error reported; base content. |
| Missing/unreadable/malformed pack asset | Asset omitted (structural report, logged warning); the card falls back to the base map and then `Fallback` art — never a crash or blank face. |
| Pack fails to load | Registry stays base-only; the game boots and renders base content. |

### Save compatibility

Main Street records the active pack set (`activePacks: { id, version }[]`) plus
the merged `csvChecksum` / `csvData` in every save. On load: the merged CSV is
restored from the save, a pack named in the save but not currently active
produces a warning and the game continues on base content, and the game refuses
to resume only when a live card instance needs a missing template
(`MissingCardPackTemplateError`, `src/MainStreetCardPacks.ts`).
`mergeMainStreetCardPool()` → `loadTemplatesFromCsv()` is the single merge entry
point.

## Regeneration commands

After changing a pack's `cards.csv` or `src/sprites/` sources:

```bash
npm run generate:pack-assets                 # pack assets (deterministic assets/<cardId>.png)
npm run build:card-pack -- --input packs     # build the installable packs root
node src/scripts/generate-main-street-card-art.mjs   # base art map (base pool only)
node src/scripts/generate-main-street-card-svgs.mjs  # static SVG fixtures (if applicable)
```


Main Street's test surface for the self-containment contract:
`PackArtRegistry.test.ts` (pack-aware resolution), `ResidentialPackArt.test.ts`
(removed pack → `Fallback`), `ResidentialPackPipelineIntegration.test.ts`
(missing asset → `Fallback` + warning; end-to-end SVG embeds the pack's `data:`
art), and `card-art.test.ts` (base-card regression).

Manual, packaged-Electron scenarios (installed/entitled, present/locked,
missing) are specified in the core
